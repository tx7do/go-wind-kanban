## ❌ 阻塞性缺口（需在上线前修复）

### 1. RBAC：board 权限码零角色绑定

**证据**：
```
sys_apis 中 Board/Card/Column/Label 相关 operation 行存在（18 条，2026-08-22 创建）
sys_role_permissions JOIN sys_permissions WHERE code LIKE '%board%' → count = 0
```

**机制**：authz 中间件 (`authz.Server(authorizer)`) 对全部 `/admin/v1/*`、`/app/v1/*` 路由生效（rest_server.go:72 确认）。它依据 `sys_role_permissions` 判定。当前 board 权限码虽登记进 `sys_apis`，但**没有任何角色绑定这些权限**。

**为何冒烟能过**：冒烟用的 tenant_admin 被手工塞了 admin 的角色（含 `platform:admin`），该角色有全局通配绑定，绕过细粒度判定。换一个干净的 tenant 普通用户 → 全员 403。

**影响**：生产环境除 platform 管理员外无人能看板。这等同于"没做权限"。

**建议**：种子脚本为 `sys:tenant_manager` 角色绑定 board 域全部 `:view/:create/:update/:delete` 权限码。

### 2. 登录验证码：前后端断裂

**证据**：
- `admin/authentication_service.go`: `const CaptchaEnabled = true`
- 登录请求 DTO 含 `captcha_id`、`captcha_value` 字段（生成代码已含）
- Flutter `LoginParams` 仅 `{username, password}`——不发送 captcha、不发送 tenant_code、不发送 client_type

**影响**：Flutter 端无法登录到 admin 网关（6600），也无法登录到需 tenant_code 的 app 网关。当前能跑是因为冒烟用 curl 手工拼了这些字段。

## ⚠️ 半成品（功能层有，端到端断）

### 3. 标签域缺实时事件广播

标签的 Create/Update/Delete/SetCardLabels 在 BFF 层**未调用 `hub.Publish`**（`label_service.go` 两端 grep publish = 0）。`realtime.proto` 的 `BoardChangeEvent` 也未定义 LABEL_* 事件类型。

**后果**：A 用户给卡片贴标，B 用户的 Flutter 端不会收到更新，直到下次全量快照拉取才对账。标签操作实时性断裂。

### 4. Flutter 标签 UI 完全缺失

`lib/src/features/board/` 下无标签选择器、无卡片标签展示。后端标签 API 可用，前端无消费方。

### 5. admin 看板页列重排回调为空

`board-detail.vue` 的 `moveColumn` 调了 `columnService.move`，但 `board_desktop_page.dart`（Flutter）的 `onMoveGroup` 回调体是空注释（"随后接入"）。即 Flutter 宽屏**列本身不能拖拽重排**，只有卡片能拖。窄屏同理。

### 6. Flutter 登录参数缺失

`LoginParams` 缺 `tenant_code`、`client_type`、`captcha_*`。其中 tenant_code 是 app 网关登录的必填项（core 据此解析租户），缺它直接 400 `invalid tenant`（冒烟时实证过）。

## ⚠️ 测试与质量缺口

### 7. 后端单测：1 项失败 + 看板域零覆盖

```
FAIL  go-wind-kanban/pkg/utils/converter  (api_test.go:60 两个 case)
```
这是预存失败（看板无关），但说明 CI 红的。

看板域（board/column/card/label repo、lexorank、broadcast hub）**没有任何后端单测**。只有 `pkg/lexorank` 有测试且通过。核心业务逻辑（Lexorank 排序、Move 邻居解析、SyncBoard 差量合并、SetCardLabels 事务差量）全靠人工冒烟，无回归保护。

### 8. Flutter 端单测覆盖薄

仅 3 项模型序列化测试。`BoardController` 的乐观更新、离线入队、重连重放、事件合并——这些复杂状态机零测试。`widget_test` 因 init 链含 NTP 网络而 skip。

### 9. 数据库无外键约束

ent schema 用 `Optional()` FK 字段 + 无 DB 层 FK 约束（FK nullability 由 repo 层 `SetXxxID` 强制）。这意味着：
- 直接 SQL 可插入孤儿卡片（column_id 指向不存在的列）
- 删除列时依赖应用层级联（board.go 的 `OnDelete:Cascade` 是 ent 注解非 DB FK）

冒烟没踩到，但生产并发或部分失败时可能产生脏数据。

## ⚠️ 安全/健壮性

### 10. WS 鉴权用 query token

`/app/v1/ws?access_token=<jwt>` —— 浏览器 history、代理日志、Referer 均会泄露 token。标准做法是握手时用 Sec-WebSocket-Protocol 头或一次性 ticket 换长期 token。当前为图浏览器 WebSocket 限制而走了最简方案。

### 11. broadcast hub 慢消费者丢事件

`dispatch()` 对满缓冲通道丢弃最旧事件（代码注释"尽力而为"）。实时性靠 SyncBoard 兜底，但若客户端长期慢，事件丢失→状态滞后。设计上可接受，但应监控丢弃率。

### 12. 客户端 _midRank 逻辑

Flutter `board_controller._midRank` 用 base-36 客户端近似中点。在线时被服务端 rank 覆盖，但离线时多张卡挤在同一列的中间位，客户端序可能与服务端最终序不一致直到重放完成。视觉抖动。

## ✅ 做得扎实的部分（值得保留）

1. **Lexorank 服务端实现**：Between 中点 + Rebalance 网格（36^6 容量），有单测，排序正确性冒烟实证（h→q→u 单调）
2. **乐观锁**：六处 `VersionEQ` 校验 + 409 返回，与服务端 version 自增配合，机制完整
3. **SyncBoard 差量合并**：known-version 对账 + upserted/deleted 分离，客户端 `_mergeDelta` 正确处理列删除连带清卡
4. **ent FK 修复**：发现并修了"O2M Required 阻断父创建"和"FK 私有字段 mapper 丢失"两个真 bug，而非绕过
5. **离线队列**：Hive 持久化 + FIFO 重放 + 重连触发，结构清晰
6. **WS E2E 验证**：真实跨服务（admin 触发 → Redis → app 订阅者收到），非 mock
